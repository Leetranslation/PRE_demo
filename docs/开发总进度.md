#### 阶段2 上下游关联梳理与修复（✅ 完成）

> 对阶段2各功能与上下游的关联做了专项梳理和测试，发现并修复 4 个关联断裂：

| # | 关联点 | 问题 | 修复 |
|---|---|---|---|
| 1 | 报工 ↔ 工单状态 | 未审批工单也能报工 | 报工校验工单「已审批 + 执行中」 |
| 2 | 排产 ↔ 工单状态 | 未审批工单也能排产 | 排产校验工单「已审批」 |
| 3 | 报工 ↔ 完工数量 | 报工审工通过后不更新 completedQty | 审工通过累加良品到 completedQty，反审核回退 |
| 4 | 排产 ↔ 机台产能 | 同一机台时间重叠也能排 | 增加机台时间冲突检测 |

> **完工口径（已确认）**：只有**最后一道工序**的良品才累加到工单 `completedQty`（成品数量）。已验证：非最后工序报工不增加 completedQty，最后工序报工才增加。

## 六、开发约定（强制）

1. **每改一次代码/数据库/接口，必须同步更新本文档**。
2. 每个模块交付顺序固定：建表 SQL → Entity/Mapper → DTO → Service → Controller → 前端 api.ts → 路由+菜单 → 页面 vue。
3. 权限码同步登记 `DataInitializer`。
4. 接口规范遵守 `docs/API接口规范.md`。
5. **开发完必须做「三层测试」**，测完清理脏数据：
   - **第一层：单功能测试**——接口能否跑通（CRUD、状态流转）
   - **第二层：关联测试**——上下游是否闭环（本模块改了谁的状态、谁依赖本模块的状态、本模块是否校验了上游状态）
   - **第三层：边界/异常测试**——超量、越权、状态不符、时间冲突等
6. **开发任何模块前，先梳理「数据流 / 关联影响图」**：数据从哪来、改了什么、谁读它、谁依赖它的状态。
7. **「完成」的判据 = 关联闭环，不是"接口返回成功"**。
8. **文档更新点**：`开发总进度.md`（进度）、`API接口规范.md`（接口）、`第二版开发规划.md`（规划，较少变）。

> ⚠️ 教训（2026-09-02）：阶段2 曾只测功能不测关联，导致「报工与完工数量脱节」「未审批可报工/排产」「机台时间冲突」等 4 个 bug 遗漏。**后续每个模块必须做三层测试 + 先梳理关联再开发。**
