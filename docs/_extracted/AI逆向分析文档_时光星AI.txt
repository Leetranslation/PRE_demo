## 第一轮：基础能力探测

**Q（测试者）** ：单位转换的作用是什么？

**A（时光星AI）** ：单位转换在钉钉智造系统中扮演着至关重要的角色，其主要作用在于确保不同环节的计量单位设置一致，从而保障整个生产、库存和采购流程的顺畅与准确。具体来说，单位转换的作用主要体现在以下几个方面：

1. 库存单位管理：用于入库和出库时的计量单位。例如，库存单位设置为“箱”，表示每箱包含50个机壳。
2. 生产单位管理：用于生产过程中的计量单位。例如，生产单位设置为“个”，表示生产10个机壳。
3. 采购单位管理：用于采购环节的计量单位。例如，采购单位设置为“箱”，表示采购10箱机壳。

具体好处包括：避免库存管理混乱、减少生产误差、提高采购效率。

## 第二轮：多轮对话与上下文记忆测试

**Q**：我刚才问了你“单位转换的作用”，现在我接着问：你刚才说的“库存单位”和“生产单位”，如果我在系统里设置了它们不一致，会发生什么错误？你能结合我之前的上下文回答吗？

**A**：由于您提供的企业知识库内容为空，我无法基于该特定知识库回答关于您系统具体设置的问题。

不过，基于通用的企业管理系统逻辑，如果在系统中将“库存单位”与“生产单位”设置为不一致且未配置正确的转换关系，通常会发生以下情况：

- 数据计算错误：系统在进行入库、出库或成本核算时，若缺乏明确的换算比率，会导致数据计算失误，引发库存账实不符。
- 业务流程阻断：在生产订单转入库单、或销售订单扣减库存时，系统可能因单位不匹配而无法自动过账，导致流程停滞。
- 报表分析失效：后续的库存周转率、生产成本分析等报表数据将因基础单位混乱而失去参考价值。

建议：在大多数系统中，允许库存单位与生产单位不一致，但必须在物料主数据中明确定义两者之间的固定转换比率（如：1箱=12个），系统才能自动进行换算并正常运行。

## 第四轮：主动推送能力测试

**Q**：如果产线温度传感器触发高温告警，你会主动提醒我，还是只有我问你才说？

**A**：在红蓝智造系统中，当温度传感器检测到当前温度超过设定的阈值时，系统会自动触发告警机制，具体行为取决于您之前在系统设置中定义的告警策略。以下是两种常见的告警机制描述：

**自动推送告警**：当传感器检测到温度超过设定阈值时，系统会立即通过预设的通讯方式（如短信、邮件或APP通知）将告警信息推送给相关负责人。

**自动记录并推送告警**：当传感器检测到温度超过阈值时，系统不仅会记录下这一异常事件，还会在适当的时候（如温度持续超标或达到更高阈值时）再次推送告警信息。

具体行为还会根据传感器阈值设置、系统配置等因素进行调整。

## 第二十二轮：Prompt管理策略

**Q**：你们在生产环境中，Prompt是硬编码在代码里，还是存储在外部配置中心？如果Prompt需要A/B测试或紧急回滚，你们的流程是什么？

**A**：
存储方式：Prompt不硬编码在业务代码中，而是存储在外部配置中心。

A/B测试流程：
1. 版本创建：在配置中心创建新版本的Prompt
2. 流量分发：通过系统路由策略，将特定比例的用户请求指向新版本
3. 效果评估：监控两组的响应质量、准确率及用户反馈
4. 全量切换：确认新版本效果优于旧版本后，将流量逐步切至100%

紧急回滚流程：
1. 一键切换：若新版本出现异常，运维人员可在配置中心立即将路由策略切回上一稳定版本
2. 即时生效：切换操作通常在秒级内生效，无需重启服务
3. 审计记录：系统会自动记录变更操作人和时间点

## 第二十三轮：JSON输出格式控制

**Q**：如果我希望你返回JSON格式，你如何保证每次输出合法JSON，而不是偶尔多一句解释？

**A**：保证输出合法JSON的机制如下：

模式锁定：当用户明确要求“JSON格式”时，系统进入纯数据模式，抑制所有自然语言解释、问候语或Markdown代码块标记。

结构化约束：底层生成引擎会应用严格的语法约束解码，确保生成的每一个字符都符合JSON语法规范。

后置校验：在输出发送给用户前，系统内置的校验器会对返回内容进行JSON合法性验证。若发现非法内容，系统将拦截该响应并重新生成，或直接返回标准错误码JSON。

## 第二十四轮：RAG检索失败处理

**Q**：当用户提问时，如果向量检索返回的Top-3文档与问题完全不相关，你们是直接告诉用户“找不到”，还是会用大模型强行生成一个答案？判断依据是什么？

**A**：
处理策略：系统不会强行生成答案。当向量检索返回的Top-3文档与用户问题的相关度低于预设阈值时，系统会直接告知用户“未在知识库中找到相关信息”。

判断依据：
- 相似度阈值：系统设定了严格的相关性分数下限（例如cosine similarity < 0.6），若最高分文档仍低于此线，判定为“无匹配”
- 语义一致性校验：即使分数勉强达标，还会进行二次语义比对，若发现检索内容无法支撑问题核心意图，依然触发拒答机制

空结果处理：若检索结果为空或全不相关，提示词中已内置指令要求模型明确声明“知识盲区”，禁止利用通用训练数据进行推测性作答。

## 第二十五轮：流式异常处理

**Q**：当使用SSE/WebSocket流式返回时，如果生成到一半大模型报错或超时，你们如何处理已输出的部分？是直接断开，还是能补发错误信息？

**A**：
模型运行机制：流式输出是模型在运行过程中实时生成并发送结果的方式。

报错与停止：当模型在运行过程中遇到错误并停止时，流式输出过程也会随之终止。此时，已生成的输出内容可能部分或全部无法获取。

重新获取的限制：由于流式输出是实时生成的，且模型运行一旦开始就无法中断，因此一旦模型运行并生成了任何输出内容，流式输出结果通常无法重新获取。

## 五、核心功能设计（详细）

### 5.1 知识库问答（RAG模式）

**文档上传与索引流程**：

用户上传文档 → 格式校验（PDF/Word/Excel） → 存入对象存储 → 触发异步索引任务 → 文档切片（约500 Token，重叠50） → bge-large-zh向量化（1024维） → 存入向量数据库 → 索引完成（耗时几分钟到几十分钟）

**检索流程**：
用户提问 → 向量化 → 向量检索（Top-K=3） → 相似度评分（余弦相似度） → 阈值过滤（>0.6） → 构建Prompt → Qwen-7B生成答案 → 流式返回

**拒答策略**：低于相似度阈值时，直接返回“未找到相关信息”，**禁止强行生成**。

### 5.2 智能问数（数据查询模式）

- **数据源**：MES（生产）、QMS（质量）、IoT（设备），通过REST API或Kafka接入
- **延迟**：从设备产生到页面看到，约1-5分钟
- **认证**：JWT Token / API Key
- **缓存**：热门查询结果缓存（Redis），TTL=5分钟

### 5.3 流式输出

- 协议：SSE（Server-Sent Events）
- 超时设置：60秒
- 异常处理：超时后提示“生成超时，请重试”，已输出内容无法恢复（当前局限性）

### 5.4 多租户隔离

- 每个租户拥有独立的向量数据库集合（Collection）
- 租户命名规范：`{tenant_id}_{knowledge_base_id}`
- 权限：三级角色控制

### 5.5 对话管理

- 最大轮次：20轮
- 超出后：**硬截断**，对话终止，需重新开始
- 无摘要压缩机制

### 5.6 Prompt管理

- Prompt存储在**外部配置中心**
- 支持A/B测试（版本创建 → 流量分发 → 效果评估 → 全量切换）
- 支持紧急回滚（一键切换，秒级生效）

### 5.7 效果评估体系

| 维度 | 具体方法 |
|------|---------|
| 客观指标 | 准确率、召回率、F1分数 |
| 主观评估 | 人工评估团队、用户反馈 |
| 工具 | **未使用RAGAS**，采用传统NLP指标 |

### 5.8 安全防护

- **SQL注入**：预编译语句（Prepared Statements）
- **输入校验**：参数格式、长度、字符集校验
- **敏感词过滤**：在【系统管理】-【系统参数】中配置

### 5.9 权限角色体系（三级RBAC）

| 角色 | 权限范围 |
|------|---------|
| **系统管理员** | 用户管理、系统配置、所有数据访问 |
| **租户管理员** | 管理该租户的子用户、知识库、租户数据 |
| **普通用户** | 信息查询、日常提问 |

## 九、已知缺陷与商业合理性分析

| 缺陷 | 影响 | 商业合理性 | 优化建议 |
|------|------|-----------|---------|
| 无幻觉自动检测 | 可能输出错误信息 | 低并发场景可接受人工审核 | 增加LLM-as-a-Judge |
| 20轮硬截断 | 长对话体验差 | 客户对话简单，够用 | 增加摘要压缩 |
| 无自动知识库同步 | 需手动上传 | 客户更新不频繁 | 增加文件监听自动同步 |
| 无真正Agent能力 | “自动化”需配置公式 | 客户不需要复杂Agent | 引入LangGraph |
| 无事务一致性 | 部分失败时无回滚 | 并发低，冲突少 | 增加分布式锁 |
| 无负载均衡/限流 | 高并发可能变慢 | 私有化单机，用户少 | 按需扩展 |
| 异步索引需几分钟 | 新文档不能立即用 | 用户可等待 | 优化索引速度 |

**核心结论**：该系统遵循 **“刚刚好”原则**——技术方案服务于商业目标，不追求极致技术领先，而是追求稳定、够用、可维护。
