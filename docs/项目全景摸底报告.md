## 0. 一句话结论

这是一个**已经跑通完整业务闭环的模块化单体 ERP + 轻量 MES**，不是 demo：后端 305 个 REST 端点全部有真实实现、无 mock；105 张表、14 个业务域、约 82 个前端页面全部落地。

它当前的状态是：**业务广度已经铺满，工程质量停在"能用"这一档**。真正的风险不在功能缺失，而在三处系统性的结构问题：

1. **并发一致性只覆盖了库存台账，没覆盖单据累计字段** —— 这是唯一会造成"账实不符"的类别（超发、超收、超领、超退）；
2. **鉴权只有功能权限，没有数据权限** —— 任何有 `sales:order` 的用户能看全公司订单；
3. **文档已经和代码分层失效** —— 接手时若读到过期章节，会把项目误判为停在一年前的阶段 2。

### 2.3 分层实事（重要认知）

**这个项目的业务逻辑不在 Mapper，100% 在 Service。**

- 101 个 Mapper 里，**100 个是纯空壳**：`@Mapper public interface XxxMapper extends BaseMapper<Xxx> {}`，零方法。
- 全项目只有 **1 处自定义 SQL**：`InventoryMapper.selectForUpdate`（`@Select` + `FOR UPDATE`，用 `<=>` 做 NULL 安全比较）。
- 另有 2 处裸 SQL 绕过了 Mapper：`SysConfigService` 和 `ProductionInboundService` 直接用 `JdbcTemplate` 查 `sys_config`。
- 没有 XML 映射文件（`resources/mapper/**` 不存在）。

**含义**：改造时不用去翻 XML，所有逻辑在 Service；但"同一能力两套实现"（`SysConfigService` vs 裸 `JdbcTemplate`）是需要统一的口子。

## 3. 后端架构要点

### 3.1 统一约定

| 项 | 实现 |
|---|---|
| 返回体 | `Result<T>` = `{code, message, data}`，成功 code=0；分页 `PageResult<T>` = `{page,pageSize,total,records}`。**305/305 端点统一，无例外** |
| 主键 | `BaseEntity` 统一 `@TableId(type = IdType.AUTO)`（两个例外，见风险清单） |
| 逻辑删除 | `deleted` 字段 + `@TableLogic`，全局配置 `logic-delete-field: deleted` |
| 自动填充 | `MybatisPlusConfig.metaObjectHandler` 填 `createTime/updateTime/createBy/updateBy/deleted=0`，操作人取自 `SecurityContextHolder` |
| 编号 | `CodeGenerator.next(prefix)` → **Redis INCR** → `前缀 + yyyyMMdd + 4位流水`，按日重置，TTL 48h |
| 幂等 | `IdempotencyService.checkAndOccupy(requestId, biz)` → Redis `setIfAbsent`，key `idempotent:{biz}:{requestId}`，TTL 24h |
| 事务 | 53 个类共 147 处 `@Transactional`，**全部是裸注解**（无 propagation/isolation/rollbackFor）。`BizException extends RuntimeException`，所以业务异常能正常回滚 |

### 3.2 鉴权模型

- JWT 无状态，`JwtAuthFilter` 解析 → 塞 `SecurityContextHolder`。**JWT 只带 userId/username，不带权限**，每次请求由 `UserDetailsServiceImpl` 从库里加载权限。
- 有效期 24h，**没有 refresh token**。
- 权限码格式 `模块:资源[:操作]`（如 `sales:order:approve`），静态路由 + 类级 `@PreAuthorize`。
- 白名单只有 4 条：`/api/auth/login`、`/swagger-ui.html`、`/swagger-ui/**`、`/v3/api-docs/**`。
- 401 和 403 是**真实 HTTP 状态码**（`SecurityConfig` 里配了 entryPoint / accessDeniedHandler），这点做得比多数项目规范。

### 3.3 库存并发模型（全项目最值得研究的一段）

`InventoryService.change(dim, direction, qty, bizType, bizId, bizNo)` 是**唯一的库存出入口**（已全量验证：没有任何地方绕写 `inventory` 表）。四层防护：

```
① Redis 分布式锁    key = inventory:lock:{itemType}:{itemId}:{warehouseId}:{stockType}:{locationId}:{batchNo}:{serialNo}
                    setIfAbsent，TTL 10s，50ms 自旋，最多等 2s，超时抛 409
                    ThreadLocal<Set> 做同线程重入（避免同事务内自我死锁）
② 行级悲观锁        SELECT * FROM inventory WHERE ... FOR UPDATE（唯一的自定义 SQL）
③ 唯一索引兜底      uk_inv_dim(item_id,item_type,warehouse_id,location_id,batch_no,serial_no,stock_type)
                    插入冲突 → 捕获 DuplicateKeyException → 重新 selectForUpdate
④ 维度归一化        normalize()：locationId→0L，batchNo/serialNo→""，与 DB DEFAULT 对齐
```

**设计得对的地方**：
- 锁在**事务提交后**释放（`TransactionSynchronization.afterCompletion`），避免"锁先释放、数据未提交"的读写窗口。
- `normalize` 消除了 MySQL 唯一索引对 NULL 不生效的经典坑。
- 出库余额校验在**持锁读到的行上**做，检查与扣减同锁内完成。

**设计有缺口的地方**：
- TTL 10s 硬编码，长事务（大单据批量 `change`）可能超租约；
- 释放锁是裸 `delete`，**没有 owner 校验**（经典"锁过期+盲删"问题，正确做法是 value 存 UUID + Lua 比对）；
- `release()`（释放预留）**完全没加锁**，用 `selectById` 读后覆盖写，与 `reserve()` 保护不对称；
- 多维度加锁顺序不固定（`TransferService` 先源仓后目标仓），双向调拨并发时会互相等到超时，退化成 409 假失败；
- `sys_config.negative_stock_strategy='forbid'` 这个配置 **代码里根本没读**，负库存策略是硬编码的。

### 3.4 MRP / 成本 / 编号三处核心算法的实际能力

**MRP（`MrpService.calculate`）—— 比预期的强**
- ✅ 多层 BOM 递归展开（`while` 逐层 + `guard<100` 防循环引用）
- ✅ 损耗率、安全库存、可用库存抵扣、在途供应抵扣（已审批未完成的采购单/生产工单）
- ✅ 提前期倒推建议日期（`需求日 - purchaseLeadDays/productionLeadDays`）
- ✅ 需求来源留痕（`sourceType/sourceId/sourceNo`）
- ❌ **无批量策略（Lot Sizing）**：没有最小订货量、包装倍数、固定批量、EOQ
- ❌ **无时间分桶（Time Phasing）**：所有需求聚成一个数量、取最早日期，不做按日/周分桶，也不做需求的先后分配（Pegging）
- ❌ **`supplyType` 判定有 bug**：product 分支无条件 `"make"`，注释写"无 BOM 则采购"但**没有这个分支** → 无 BOM 的产品被建议自制 → 转成无 BOM 的工单 → 领料时报"该工单无 BOM，无法领料"，**死路**
- ❌ **无幂等无锁**：重复点"计算"会生成多份 plan

**MPS（`MpsPlanService`）—— 名不符实**
只有"计划登记 + 转工单"两个方法，**没有任何 MPS 运算**（无预测、无 ATP、无毛净需求、无 BOM 展开、无产能校验）。

**成本核算（`CostService`）—— 标准成本法，且有一处量纲错误**
- 方法：**标准成本法**（读 `material.standard_cost` / `product.standard_cost`），**不是移动加权平均**。
- `Inventory.unitCost/totalCost` 两个字段**全项目从未被写入**，是死字段。
- 公式：
  ```
  材料成本 = Σ( bomItem.quantity × (1+lossRate) × 子件标准成本 )
  人工成本 = Σ 已审报工，按 process.priceType：time→标准价×工时 / piece→标准价×良品数 / 其他→固定价
  制造费用 = 材料成本 × sys_config.overhead_rate
  单位成本 = 总成本 / completedQty
  ```
- ⚠️ **量纲错误（已亲自复核 `CostService.java:82-94`）**：`calcMaterialCost` **没有乘工单数量**。`bomItem.quantity` 是单件用量，所以算出的是**单件材料成本**；而人工/制造费用是整单的。三者相加再除以数量 → **材料成本被低估约"工单数量"倍**。正确应为 `Σ(单件用量 × 工单数量 × (1+损耗) × 标准成本)`。
- 只做一级 BOM，不递归（与 MRP 的多级口径不一致）。

**单据编号（`CodeGenerator`）**
- Redis `INCR` 原子递增，多实例安全。但有四个缺口：① 超 9999 单 `%04d` 溢出成 5 位；② `expire` 只在 `seq==1` 时设，key 若已存在且无 TTL 会永久驻留；③ Redis 不可用时所有建单接口直接不可用（无 DB 兜底）；④ 前缀 `GY` 被供应商和工艺路线**重复占用**。

### 4.2 数据模型层面的隐患

- **零外键**：所有建表脚本被 `SET FOREIGN_KEY_CHECKS = 0/1` 包裹，全靠索引；删除主子单据无 DB 层拦截。
- **零乐观锁**：全项目没有 `@Version`，也没注册 `OptimisticLockerInnerInterceptor`。
- **状态字段全是 String 魔法值**，无枚举、无 CHECK、无字典约束。清点出 30+ 种状态字面量。最典型的坑：`production_order` 的 `qc_status` 用 `"pending"` 表示"待质检"，而同一行 `approve_status` 的 `"pending"` 表示"待提交"——**同一实体、同一字面量、两种语义**。
- **金额/数量类型统一用 `BigDecimal`**（这点做得对，全项目没发现金额用 double/float），但**精度定义冲突**：`tax_rate` 在不同表里分别是 `DECIMAL(10,2)` 和 `DECIMAL(6,2)`；单价 `price` 在明细里是 `(18,6)`、在 `customer_price` 里是 `(18,2)`。另外 `tax_rate` 存的是**百分数 13**，不是 0.13 —— 新写的税额计算若按小数处理会错 100 倍。
- **"物料/产品 ID"三种命名并存**：`itemId`（库存/盘点/调拨/质检/外协）vs `productId`（销售明细）vs `materialId`（采购明细/领料/组装）vs `childId`（BOM）。**无法跨模块泛化处理**。
- **`order_id` 一词多义**：在 `purchase_inbound` 指采购订单、在 `production_inbound` 指生产工单、在 `sales_invoice` 指销售订单、在 `outsource_order` 指生产工单。
- **单据状态机形同虚设**：`sales_outbound`/`purchase_inbound`/`production_inbound`/`material_issue`/`material_return`/`transfer`/`other_stock`/`assembly_order` 的 `status` **默认值就是终态 `'completed'`**，落库即完成，**没有草稿/审核中间态，无法作废/红冲**。这与 `production_order` 那套 8 状态的精细设计风格完全割裂。
- **两套并行的核销模型**：销售侧 `sales_verification`（挂在发票上）vs 财务侧 `receipt + receipt_writeoff`（挂在应收台账上）。采购侧对称。**同一笔回款两条记账路径，对账口径可能不一致**。

## 5. 业务主线与状态机

### 5.1 验收主链

```
客户/供应商/物料/产品/BOM
      ↓
   销售订单 ──审批──→ MRP 运算 ──→ 建议 ──确认──→ 采购订单 ──审批──→ 采购入库 ──→ 库存
      │                          └→ 生产工单 ──审批──→ 领料 ──→ 报工/审工 ──→ 生产入库 ──↗
      │                                                              ↓
      └────────────────────────────────────────────────────→ 销售出库 ──→ 订单完成
                                                                   ↓
                                                      发票 → 核销 → 应收 → 收款/核销
```

### 5.2 关键状态机

**审批状态**（全单据统一）：`pending`（待提交）→ `approving`（审批中）→ `approved`（已审批），`unApprove` 可回退。
**销售/采购订单业务态**：`pending_outbound/pending_inbound` → `partial_*` → `completed`。
**生产工单**：审批 `pending→approving→approved`；业务 `pending→producing→finished`；另有 6 个子状态 `finishStatus/inboundStatus/issueStatus/qcStatus/machineStatus/outsourceStatus`。
**外协单**：审批同上；业务 `pending→outsourcing→finished/voided`。
**报工**：`pending→approved/rejected`（`batchApprove` 支持一键批量）。
**MRP 计划**：`calculated→confirmed`。
**质检申请**：`pending→inspecting→finished`。

### 5.3 已建立的审核规则（值得肯定的部分）

- 审批**禁止自审**：`sys_config.allow_self_approve=false`，11 处 `checkSelfApprove`。
- 反审核有**业务阻断**：已出库不能反审核订单、已领料不能反审核工单、已核销不能反审核发票。
- 排产有**机台时间冲突检测**：`status in (planned,started) AND plan_start < 新end AND plan_end > 新start` → 冲突抛异常。
- 领料有**防超领**：`本次量 ≤ BOM需求 - 已领累计`。
- 入库有**开工序开关**：`sys_config.require_issue_before_inbound`。

## 6. 前端架构

### 6.1 数据流

```
页面 → api/*.ts → utils/request.ts（axios，baseURL='/api'）
      → 请求拦截器注入 Bearer token（读 localStorage）
      → 响应拦截器：code===0 → 直接 return data（剥壳）
                     code!==0 → ElMessage.error + reject
                     HTTP 401 → 清 token + 跳 /login
                     HTTP 403 → 提示无权限
```

### 6.2 三个结构性特征

**① 路由和菜单是两份独立硬编码，纯手工同步**

`router/index.ts`（81 条静态路由，全量注册，无动态 `addRoute`）和 `layout/menuConfig.ts`（14 项一级菜单 + 多列浮层分组）是**两个互不引用的文件**，只在路径字符串上约定一致。新增页面必须**同时改两处**，无任何编译期/运行期校验。

**② 前端零权限体系**

登录接口只返回 token/username/realName，**不返回权限列表**。所以：菜单全量展示、路由全量注册、按钮全量渲染，用户点下去才被后端 403 挡回来。后端权限模型是合规的，前端是不合规的。

**③ 高度模板化，但重复代码量巨大**

82 个页面里 **81 个**用了完全相同的 4 个 class（`.filter-bar` / `.toolbar` / `.pagination`），**约 50 个页面**逐字复制同一组 6 个函数（`load/handleSearch/handleReset/openDialog/handleSave/toggleStatus`）。

可量化的重复：
- `approveText/approveTagType` 审批状态字典：**15 份拷贝**
- 打印 5 件套：**21 个文件**
- 金额大写 `upperAmount()` + `doPrint()`：**2 份完全一致**（`PrintDialog.vue` 与 `sales/order.vue`）
- 名称映射函数 `xxxName(id) = arr.find(...)`：**30+ 处各写一遍**
- `crypto.randomUUID()` 幂等键：11 处手写
- 下拉全量拉取 `{page:1, pageSize:200}`：30+ 处

**唯一的好范式**：`components/DocList.vue` 把"工具栏+导出+表格+明细/打印+分页"全封装，使用者只需传 `columns/fetchList/fetchItems/printCols`。5 个页面用了它，平均 **68 行**（对比 `sales/order.vue` 553 行）。**这是二次开发应该推广的目标形态。**

### 6.3 大文件

| 文件 | 行数 | 超长原因 |
|---|---|---|
| `views/sales/order.vue` | **553** | 自研打印（复制了 PrintDialog 的 64 行模板+24 行大写金额+22 行 doPrint）+ 5 个弹窗塞一页 + 两个 `<style>` 块 |
| `views/production/order.vue` | **530** | 领料/退料/入库三个近乎同构的弹窗 + 4 个 loader + 3 个逐字重复的 handler |
| `views/purchase/order.vue` | 461 | 与 sales/order.vue 同构度约 80% |

其余最大 297 行（`base/bom.vue`）。

### 6.4 TypeScript 是"名义 TS"

82/82 页面用了 `<script setup lang="ts">`，`tsconfig.json` 也开了 `strict: true`，但：
- **业务实体类型定义：0 个**。没有任何 `interface SalesOrder`。
- api 层返回一律 `as Promise<PageResult<any>>`，入参一律 `params: any`。
- `any` 在 views 目录命中 **641 行**。

### 6.5 工程化缺失

无 ESLint、无 Prettier、无测试（无 vitest/playwright）、无 `.env`、无锁文件。

## 9. 二次开发的建议路线

### 第一优先：修 P0（数据正确性）
