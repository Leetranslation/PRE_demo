## ⚠️ 前提修正（2026-09-16 晚，以此节为准，第四节已作废）

**用户补充了关键背景，导致原方案的技术选型判断需要反转：**

1. **这是求职作品，不是产品交付。** 目标是做出 AI 项目去应聘 AI 应用开发岗。
2. **技术栈要用 Python。** AI 应用开发招聘的要求普遍是 Python + LangChain/LangGraph + FastAPI。
3. **部署到阿里云服务器，不交付客户。** 所以"私有化交付给中小制造企业"的各种约束（不能多装进程、客户数据不能出网等）**全部不成立**。

→ **结论：原第四节"用 Spring AI / LangChain4j 替代 Python 栈"的建议作废。改用 Python 主栈。**

### 修正后的技术栈（对齐招聘要求）

| 层级 | 选型 | 对应招聘要求 |
|---|---|---|

### 与 Java ERP 的关系（关键定位）

Python AI 服务**独立成一个项目**，通过 REST 调用现有 Java ERP 取业务数据。

这样做的价值：招聘里明确写了「**能独立完成 AI 模块与 B 端业务系统（CRM/ERP）联调开发**」和「**有制造业 MES/PLM/QMS/WMS 相关 AI 功能落地经验**」—— **你手上已经有真 ERP，这是绝大多数转 AI 的候选人没有的差异化。**

| AI 功能 | Java 侧 Bug 清单是否还重要 |

## 一、先说这份资料的性质（很重要，决定你怎么用它）

**它不是技术文档，是一份「面试作品」。**

文档自己写明：「基于对"时光星AI"产品的系统性黑盒测试与逆向分析」。作者对一款商用 ERP 内置 AI 助手做了约 40 轮提问，然后把**产品的回答**整理成了一份"系统设计文档"。

这带来一个根本问题：**文档里大部分"系统设计"是 LLM 对自己架构的自述，不是经过验证的事实。**

## 二、可直接拿来用的技术参数

这些是文档里数值明确、且符合工程常识的部分，可以作为你的**起点默认值**：

| 参数 | 文档值 | 我的评价 |
|---|---|---|
| 切片大小 | ~500 token | 偏保守但可用。**但 ERP 文档多为字段表和参数说明，必须做表格/标题感知切分**，否则会把"字段名 \| 含义"切两半，检索出垃圾 |
| 切片重叠 | 50 token | 合理，10% 重叠 |
| Embedding | bge-large-zh，1024 维 | **选型正确**。中文场景 bge 系列确实是主流选择。现在可考虑 bge-m3（多粒度、支持长文本、自带稀疏检索） |
| 检索 Top-K | 3 | **偏小**。ERP 问答经常要跨多个字段综合，建议 **5-8 再 rerank 收敛** |
| 相似度阈值 | cosine > 0.6 | **方向对，绝对值不可移植**。阈值强依赖模型和归一化方式，必须用你自己的语料标定（取有答案/无答案问题各一批，找 ROC 拐点） |
| 拒答策略 | 低于阈值直接拒答，禁止强行生成 | **必须照抄**，这是 RAG 质量的生命线 |
| Rerank | 文档里**完全没提** | **漏了一环**。`bge-reranker` 对召回精度提升显著、成本极低，应该加 |
| 流式 | SSE，超时 60s | 合理。注意：无断点恢复（文档自己也承认，第 25 轮） |
| 对话轮次 | 20 轮硬截断，无摘要 | **不要抄**（见第三节） |
| 权限 | 三级 RBAC（系统管理员/租户管理员/普通用户） | 与你们现有 `role` 体系可对齐 |
| 多租户 | 每租户独立向量集合，命名 `{tenant_id}_{kb_id}` | 你们是**单租户私有化**，第一版不需要 |
| Prompt 管理 | 外置配置中心 + A/B + 秒级回滚 | **值得抄**。即使不做配置中心，也应把 Prompt 存到 `sys_config` 或独立表，不要硬编码 |
| 评估 | 准确率/召回率/F1 + 人工；**未用 RAGAS** | 起步够用。建议后续补 RAGAS 或自建 LLM-as-a-Judge 做回归 |
| 数据延迟 | 1-5 分钟（Kafka） | 见第四节的取舍建议 |

## 三、不要抄的 4 个设计

| # | 原设计 | 问题 | 你应该怎么做 |
|---|---|---|---|
| 1 | **两份知识库（知识库问答 / 企业知识库问答）互不通用**，切模式要重新上传 | 极差的用户体验，且是纯粹的实现债务 | **一个知识库 + 权限范围过滤**。文档归属部门/角色，检索时按当前用户权限过滤 |
| 2 | **20 轮硬截断、无摘要压缩** | 让用户"重新开始"是不可接受的；制造业问答经常需要多轮追问 | **第一天就做摘要压缩**（超阈值时把早期对话摘要成一段 system 上下文） |
| 3 | **无幻觉检测、无强制引用** | 这在 ERP 场景是危险的：单位换算、库存数量、税率、交期答错一次就是生产事故 | **强制三件事**：① 回答必须附原文片段引用 ② 阈值不达标直接拒答 ③ 关键数值（数量/金额/日期）做二次校验或明确标注"需人工确认" |
| 4 | **无真正的 Agent 执行能力**（只能用"公式管理"配规则） | 这既是它的短板，**也是你的差异化机会** | 但**必须先解决可回滚**（Bug 清单批次 5：库存单据无作废/红冲）。否则 Agent 出错无法修正 |

## 四、关键：这份文档是 Python 栈，你的项目是 Java

**这是最容易踩的坑：文档里的技术选型一个都不能直接用。**

| 文档选型（Python 生态） | 你的项目应该用 | 理由 |
|---|---|---|
| FastAPI + Uvicorn | **Spring Boot（保持现有）** | 不要为一个 AI 模块引入第二套后端。SSE 流式用 Spring 的 `SseEmitter`，或引入 WebFlux 用 `Flux<ServerSentEvent>` |
| LangChain / LlamaIndex | **Spring AI** 或 **LangChain4j** | Java 生态对应物。LangChain4j 对国产模型和中文 RAG 的适配更积极；Spring AI 与 Spring Boot 集成更顺 |
| Qwen-7B 本地 GPU 推理 | **先云 API 打通，再评估本地化** | ERP 是私有化交付，最终大概率要本地；但先用云 API 把链路和效果验证完，避免卡在环境上 |
| Chroma（单机）/ Milvus（集群） | **Qdrant**（推荐，轻量）/ Milvus / Elasticsearch | 你已有 MySQL 8（**无 vector 类型**）和 Redis。必须引入独立向量库服务。若要混合检索（关键词+语义）选 ES |
| bge-large-zh（PyTorch 模型） | **通过 HTTP 调用独立推理服务**（Ollama / TEI / Xinference） | **千万不要试图在 JVM 里跑 Transformer**。用 sidecar 服务，Java 侧只做 HTTP 客户端 |
| Celery + Redis | **`@Async` + 线程池**，或 Quartz / xxl-job | ⚠️ **你项目当前完全没有异步基础设施**（我实测过：无 `@EnableScheduling`、无 `@Scheduled`、无 `@Async`、无线程池）→ 必须先补 |
| Apache Kafka | **先不上**，用 Redis 队列或直接 `@Async` | 你是单体 ERP、私有化、低并发（文档自己也说客户通常 <5 人同时在线）。Kafka 是**过度设计**，只会增加部署负担 |
| JWT + API Key | **复用现有 JWT**，但补数据权限 | 见第五节第 4 条 |
| OSS / MinIO | **MinIO** 或本地磁盘 | 私有化部署用 MinIO 最省事；单机演示直接用磁盘也行 |
| Vue 3 / React | **复用现有 Vue 3 + Element Plus** | 对话 UI 直接做成 ERP 内的一个页面 + 一个路由项（记得同步改 `router/index.ts` 和 `layout/menuConfig.ts`） |

## 五、你项目当前的 5 个真实阻碍

| # | 阻碍 | 现状（实测） | 影响 |
|---|---|---|---|
| 1 | **没有只读数据源** | 现在只有 `root / <见 .env 的 DB_PASSWORD>`，无只读账号 | 「智能问数」类功能的前提。**绝不能让 LLM 直连库** |
| 2 | **没有异步/调度基础设施** | 全项目无 `@Async`、无 `@Scheduled`、无 Quartz、无线程池 | 文档索引必须异步；LLM 调用耗时数秒会阻塞 Tomcat 线程 |
| 3 | **没有向量库** | 无任何向量存储 | 新增一个 Docker 服务（建议 Qdrant） |
| 4 | **没有数据权限** | `Role.data_scope` 建了但从未用于查询过滤 | 问答要按人的权限范围答，否则 A 部门能问出 B 部门的成本数据 |
| 5 | **29 处实体入参接口** | 14 个 Controller 直接把实体当 `@RequestBody` | 若把这些暴露成 Agent tool，等于开放用户/角色管理后台 |

## 六、建议的最小落地路径

> 原则：**先只读、后写；先文档、后数据；先把链路跑通，再谈智能。**

### 第 1 步 · 纯文档问答（1 周内可跑通，零风险）
完全不碰 ERP 业务数据，只做文档 RAG：

```
用户上传 PDF/Word  →  MinIO 存原始文件  →  @Async 异步切片
   →  bge 向量化（HTTP 调推理服务）  →  Qdrant 入库
   →  用户提问  →  向量检索(5-8) + rerank  →  阈值判定
   →  Spring AI / LangChain4j 组装 Prompt  →  SseEmitter 流式返回 + 原文引用
```

这一步**不受任何现有 Bug 影响**，可以立刻开工。价值：把 Agent 框架、鉴权、审计这套地基先跑通。

### 第 2 步 · 接入业务数据问答（语义查询层，**不是 NL2SQL 直连**）

```
LLM  →  只能调用预定义参数的「语义查询工具」（如 query_inventory(itemCode, warehouse)）
     →  工具内部走只读数据源（白名单视图）
     →  AST 校验 + 强制 LIMIT + 超时 + 敏感字段脱敏（成本/毛利/银行账号）
```

### 第 3 步 · 补权限与审计
`data_scope` 落进查询过滤（B-32）；所有问答与查询落 `operation_log`（B-24），记录 trace_id / 提问 / 检索到的片段 / 模型版本 / 耗时。

### 第 4 步 · 才谈 Agent 执行能力
这一步才需要 Bug 清单的批次 1（幂等）+ 批次 2（MRP 链路）+ 批次 5（审计与红冲）。

## 七、三个需要你拍板的决策

| # | 决策 | 选项与影响 |
|---|---|---|
| 1 | **模型：云 API 还是本地私有化？** | 云 API：一周能跑通，但客户私有化场景未必接受、数据出网合规风险。本地：一次性投入 GPU，工期长。**建议先云 API 验证效果，架构上把模型调用抽象成可切换的接口** |
| 2 | **向量库选哪个？** | Qdrant：轻、部署简单、性能好（推荐起步）。Milvus：重，适合上规模。Elasticsearch：能同时做关键词+语义混合检索，但资源占用大。**若你们集群里已有 ES，选 ES** |
| 3 | **知识库的数据范围？** | 只吃外部文档（最简）／ 还要吃 ERP 业务数据（需第 2 步）／ 还要吃单据附件（需先补 `attachment` 落地，见 Bug 清单 B-28） |
